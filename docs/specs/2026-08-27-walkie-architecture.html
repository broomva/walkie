walkie — architecture and stack

A rethought app runtime for agentic workspaces. An agent session at the core governs the others; voice and chat are channels onto it.

BRO-2362 · 2026-08-27 · supersedes the architecture recorded in the walkie README before this date

This document is decided, not a survey. Where two options were live, one was picked and the reason is stated. Every vendor claim carries a source; where a vendor does not document something, it is marked unknown rather than guessed.

What walkie is, after review

The original framing was: talk to your agents, and they talk back. Adversarial review moved it. The finding that moved it is not technical:

Every ask worth escalating was escalated because a human needed to see evidence — a diff, a failure, a blast radius. Voice replaces a reviewable, logged, textual approval with an ephemeral acoustic one, summarised by the same agent that wants the yes, and leaves no audit artifact.

That degrades decision quality in proportion to how consequential the decision is. Compounding it, the handback-contract measurements say 81% of blockers were knowable at hour 0 — the bottleneck is ask quality, not ask transport.

The resolution is not to make voice weaker. It is to stop treating voice as the product. Voice is one channel onto a runtime, and the runtime decides when voice is the wrong channel.

voice Triage, status, and low-stakes answers. What is blocked, what changed, read me the last turn, pick between two options an agent already enumerated. Answered in-call, in under two seconds, from state already held.

escalate Anything needing evidence moves to chat, and the runtime is what notices. A consequential ask, a request too complex to say out loud, or a call where recognition is failing — the runtime hands the same conversation to a screen, where the diff is visible and the approval is logged. Genesis already renders this surface; walkie does not invent it.

That is a better answer to the evidence problem than restricting voice by category would have been, because the boundary is judged per-ask rather than guessed in advance. It also means a poor acoustic environment degrades the channel, not the product.

Why the core is an agent, and what the substrate still owns

One justification for an agent at the core was false and is worth recording as dead. The belief that switching a realtime voice session between workspaces is hard is contradicted by the API. From OpenAI's client-events reference, verbatim:

The client may send this event at any time to update any field except for voice and model.

tools and instructions are both swappable mid-call, so selecting a workspace is one session.update. Nothing needs an agent for that.

The justification that survives is a different one: triage is a judgment call. Deciding that four of eleven pending asks are worth interrupting a person for, that two can be answered from what is already known, and that one needs a screen because the diff matters — that is not routing. A deterministic service can dispatch; it cannot weigh. Neither can it notice that recognition is failing and move the conversation to chat, or decide which of thirty sessions to wake and what to ask them.

An earlier revision of this document killed the agent anyway. That was an over-correction: a refuted justification was used to remove a component that a better justification supports. The two objections raised against it were about implementation, and both have fixes that were already specified elsewhere in this document:

ObjectionWhy it does not bind
A single session serializes every workspace behind one turn chain, so an urgent ask queues behind a ten-minute turn.Only if the runtime does the work. It decides and delegates: its turns are seconds, and the ten-minute turn belongs to a worker. Genesis's admission gate already refuses rather than queues, which surfaces contention instead of hiding it.
Compaction silently destroys ticket-to-workspace bindings, producing confident wrong readbacks.Only if bindings live in context. They live in Postgres and are queried. The runtime is required to hold no state it could look up — which is the same rule that makes it restartable.

So the split is: the substrate is what must be correct; the runtime is what must be smart. State, transport, idempotent delivery and allowlists are deterministic and observable. Triage, channel choice and orchestration are the agent's.

How the runtime stays awake

It is not a daemon to babysit. It is a Genesis-managed session with its own cadence — woken by an event on the ask log, by /loop for a recurring sweep, or by /schedule for time-triggered work. Between wakes it costs nothing. Genesis already owns spawn, --resume continuity through a persisted session id, and a per-session worktree, so session longevity is not a problem walkie has to solve.

The connection flow

Concretely, and with the parts that are easy to get wrong called out.

  1. Client asks the service for a session. The service calls POST /v1/realtime/client_secrets with the API key. TTL is settable from 10 to 7200 seconds, default 600. The TTL governs session creation only — "The session itself may continue after that time once started" — so a ten-minute secret does not end a sixty-minute call, and there is no refresh endpoint because none is needed.
  2. Client does the SDP exchange itself. Raw SDP body, Content-Type: application/sdp, bearer of the ephemeral key. This is not the multipart form; that is the server-side unified flow.
  3. Client relays the call id to the service. The response body is a raw SDP answer, not JSON — the call id arrives in the Location header as /v1/realtime/calls/rtc_…. In the ephemeral flow only the client sees it, so relaying it is a required step, not an optimisation.
  4. Service opens a sideband. wss://api.openai.com/v1/realtime?call_id=… with the standard API key. Per OpenAI's server-controls guide this is a second connection to the same session that "can be used to monitor the session, update instructions, and respond to tool calls", and it behaves like any other Realtime connection — the full client-event surface is available server-side. No plan gate, standard API key.
  5. Tools are served by the service, not the client. Tool calls arrive on the sideband; the service answers them and injects results with conversation.item.create + response.create.
  6. Workspace switch is a session.update swapping tools and instructions for the selected workspace. This is what the channel filter in the UI actually does.

Push-to-talk is not the default mode

Hold-to-talk requires turn_detection: null, and on WebRTC audio flows continuously over the media track, so the buffer must be managed explicitly: input_audio_buffer.clear on press, commit then response.create on release, and output_audio_buffer.clear to barge in. This differs from the WebSocket flow; assuming they are the same is a documented way to ship a broken button.

Two binding constraints

Both are properties of the Realtime API that the design must absorb, and both are invisible at runtime.

constraint The 60-minute session cap is undetectable. The cap is documented. What happens at it is not, and there is no expiry event, no warning, and no disconnect-reason field — the only session.* server events are session.created and session.updated.

Design response: the client tracks elapsed time from session.created and proactively re-establishes before the cap, re-seeding context from Postgres. Never rely on a disconnect to tell you why.

constraint Context truncation is silent and lossy. When the window fills, the API drops the oldest messages with no summarization and no error. The user's original question can vanish mid-conversation while the model keeps answering fluently.

Design response: the conversation is never the source of truth. Every ask, ticket and binding lives in Postgres; the call carries a projection of that state, re-seeded on each new session. Set session.truncation deliberately rather than taking the default.

The consequence that is easy to miss

Billing is per token and idle time is free — "There is no cost currently for network bandwidth or connections" — so holding a call open while an agent works costs nothing. But the whole conversation is re-sent on every response, so per-turn cost rises through a session, and every async answer injected into a live call permanently enlarges what is re-billed afterwards. Long calls are cheap to hold and expensive to use. That asymmetry, not idle cost, is what should shape session lifetime.

The service splits in two, and this is structural

Reaching a Claude Code session works over a unix socket under /tmp/cc-socks/, and the security boundary is same-UID trust on one machine. A Railway container is neither. So:

  • Cloud half (Railway): ephemeral secrets, the sideband, SSE fan-out, artifact serving, push. Holds no ability to reach a session.
  • Host agent (workstation or the VPS): the only component that can talk to sessions. Reaches the cloud half outbound over Tailscale; nothing inbound is exposed.

Treating this as one deployable is the mistake that makes the whole thing undeployable.

Reaching worker sessions

Three supported paths exist. This was the single largest unknown at the start and it is now closed.

PathStatusVerdict
Cross-session inbox socketGA since v2.1.224Chosen. Docs explicitly sanction "a script or hook to post into a session". Proven end-to-end here: a session left idle in tmux was woken and made to execute by a plain Python script that was not a Claude Code child.
Custom channelResearch previewPurpose-built, and the only one with a documented reply path. Its contract may change. Worth adopting once stable.
Genesis claude -p + --resumeIn productionSidesteps session longevity entirely by making every turn a fresh process. The right answer for work walkie originates, as opposed to sessions it observes.

trap A receiver that bypasses permission prompts holds inbound messages rather than delivering them. Claude Code holds each message for approval and drops it after five minutes unless the sender attests its own permission class — and an HTTP service cannot. The naive build silently swallows every message.

Needing the setting that fixes this is itself the warning: it is the same lever that turns fan-out into the permission-laundering risk below. Do not reach for it without reading that section.

Delivery: one log, not two branches

The earlier design said "if the call is open, inject; otherwise notify". That is a decision made at one instant about a condition that changes continuously, and review enumerated six states where the user gets nothing or gets it twice — answer injected into a session torn down mid-round-trip; push fired and then the call reopens and also delivers; an injection landing mid-utterance and reordering against a response already generated; three answers arriving out of order across separate pushes; a call the server believes is open after a network switch killed it; a push whose artifact fetch is suspended while the phone is locked.

Replace the branch with an append-only per-user ask log. Both the injection path and the push path become views over it, each idempotent and individually ackable. Delivery becomes pull-based with explicit acknowledgement, so "the user actually heard it" is a state the system can represent — which under the branch design it simply cannot.

Security

This is voice-adjacent code execution on a machine with dozens of live sessions. Four risks survived review and are design inputs, not afterthoughts.

1 Cross-session permission laundering. Voice → service → a session with different permissions is a pattern the harness contract explicitly prohibits. Making unattended fan-out work pushes toward flattening permissions everywhere, which converts one spoken word into unreviewed execution across every repository.

Response: the host agent carries its own allowlist of which workspaces are reachable by voice at all, defaulting to none. Triage-only scoping means the common path never needs elevated permissions.

2 Injection with an audio exfiltration channel. Worker output derives from repository content — READMEs, changelogs, postinstall banners, PR comments. Free text that gets actioned is a path from a crafted string to other workspaces, and the result is read aloud.

Response: an ask is structured data — ticket id, an enum, bounded fields — never free text. The service must be structurally unable to originate a workspace call from a worker-supplied string.

3 Earshot is authentication. Anyone nearby is a principal, and barge-in is designed to yield to any incoming voice. Genesis's phone mitigation — deliver to the number on file — protects the readback, not the authority; the dangerous payload here is the word "yes".

Response: triage-only scoping. Nothing consequential is authorizable by voice, so a stranger's "yes" reaches nothing that matters.

4 Fail-open has precedent in this codebase. Genesis's unauthorized() returns false when no token is configured, and the WhatsApp arc recorded the full failure shape: an allowlist bug denies everything, the bot looks dead, the operator sets the open flag, and every sender gets a shell.

Response: the service refuses to start without its secrets rather than starting permissive, and the pairing flow is built to be obviously working so nobody reaches for the bypass.

Build plan

Dependency-ordered. Each milestone is useful alone and retires a named risk. Milestone 1 is deliberately the smallest thing that tests the assumption most likely to be wrong.

Milestones 1 and 2 need no OpenAI account, no Apple account, and no deploy. They are worth doing before any decision about the rest is made.

Note what is not a milestone: standing up the runtime session. Genesis already spawns and resumes Claude Code sessions in per-session worktrees, and /loop and /schedule already give a session its own cadence. The runtime is a Genesis session with a brief, not a new piece of infrastructure — which is why milestone 1 is about reaching other sessions rather than about creating this one.

What this document does not cover

Three things were deliberately left out rather than guessed. ElevenLabs' execution_mode: "async" exists and is described as best for long-running operations, but appears only in API-reference schema dumps with no statement of whether an async result ever reaches the model — it is not designed on here. Neither vendor documents a resume path after a network drop, so reconnection is treated as a new session plus re-seed. And no tool-result timeout is documented on OpenAI Realtime, which is convenient for holding a call open while an agent works, but is an absence of documentation rather than a guarantee.

Sources are linked inline and every vendor claim was read on the vendor's own documentation. Two claims in earlier revisions of the walkie README were wrong and are corrected here: that switching workspaces mid-call is hard, and that the cross-session messaging socket is undocumented. The second was mine. The router architecture that both errors supported has been removed rather than patched.
